# Dans chaque [formulaire](https://accessibilite.numerique.gouv.fr/methode/glossaire/#formulaire), le [contrôle de saisie](https://accessibilite.numerique.gouv.fr/methode/glossaire/#controle-de-saisie-formulaire) est-il utilisé de manière pertinente (hors cas particuliers) ?

<CriteriaA/>
<IconedLink>[Lien RGAA](https://accessibilite.numerique.gouv.fr/methode/criteres-et-tests/#11.10)</IconedLink>
<BookmarkletTags names={["11.1 Formulaires"]} />

## Que vérifie-t-on ?

### Champs obligatoires

Les champs obligatoires doivent être identifiés **de manière visible**. Plusieurs méthodes disponibles :
- un texte générique **avant** le formulaire : « tous les champs sont obligatoires »
- l’utilisation d’un astérisque, qui sera définie avant le formulaire: « * : champs obligatoires »
- directement dans le nom accessible (et le nom visible)

_Note : l’utilisation de `required` ou `aria-required="true"` ne rendant pas l’information visible
à tous les utilisateurs (mais uniquement disponible pour les utilisateurs aveugles), même si ces propriétés
sont présentes, elles doivent toujours être doublées d’un texte visible informant du caractère obligatoire._

<details>
    <summary>
        #### Exemples
    </summary>

    <Example imgImport={CParuVendu} comply>
        Sur le site [paruvendu.fr](https://www.paruvendu.fr/communfo/deposegeneriquefo/responsive/depose?choixFamille=IVH00000&kw=),
        dans le formulaire de publication d’une annonce, un texte visible avant le formulaire permet d’identifier
        les champs obligatoires.
    </Example>
</details>

#### Aide à la détection
- Soumettre le formulaire à vide et vérifier la présence de message d’erreur indiquant des champs obligatoires.
- Si des champs sont obligatoires, vérifier qu’ils peuvent être identifiés pour tous les utilisateurs
(message visible accessible).

### Format contrôlé

Pour tous les champs dont **le format de saisie est contrôlé** :
- le **format attendu** est indiqué de manière visible **avant la soumission du formulaire**

_**Cas typiques :** email, téléphone, code postal, IBAN, mot de passe._

<details>
    <summary>
        #### Exemples
    </summary>

    <Example imgImport={NCMarseille}>
        Sur la page d’accueil de [marseille.fr](https://www.marseille.fr/), en bas de page, le formulaire
        d’inscription à la lettre d’information demande une adresse email dont le format est contrôlé.
        Le format n’est pas indiqué.

        Pour corriger, on pourra recommander d’ajouter un texte visible qui mentionne le format attendu :
        « nomprenom@domain.fr », qui soit correctement relié (par ex. avec la liaison `aria-describedby`)
    </Example>

    <Example imgImport={NCAmeli}>
        Sur le formulaire de création de compte [assure.ameli.fr](https://assure.ameli.fr/PortailAS/appmanager/PortailAS/assure?_nfpb=true&_pageLabel=as_creation_immediate_page),
        le format de saisie pour la date de naissance est donné dans l’attribut `placeholder`,
        qui n’est pas une implémentation conforme. On pourra recommander l’ajout d’un texte visible accolé au champ,
        avec un attribut `id` et relié par la liaison `aria-describedby` déjà présente (on proposera donc d’ajouter
        l’identifiant du passage de texte ajouté).

        **Important :** puisque la propriété `aria-describedby` est déjà présente sur le champ, et que le champ a déjà
        une étiquette reliée, l’ajout d’un `title` serait sans effet puisque selon les calculs du nom et de
        description accessible, il ne sera pas pris en compte.
    </Example>

    <Example imgImport={CToulouse} comply>
        Dans le formulaire de contact de [Toulouse Métropole](https://metropole.toulouse.fr/nous-contacter),
        les champs qui attendent un format particulier (l’email par exemple) propose une indication visible du
        format qui est correctement relié au champ (voir la description remontée par le bookmarklet).
    </Example>
</details>

### Messages d'erreur
Les messages d’aide et les messages d’erreur doivent être correctement reliés aux champs respectifs.
- étiquette
- attribut `title`
- attribut `aria-describedby="id_dun_texte"`

<details>
    <summary>
        #### Exemples
    </summary>

    <Example comply>
        ```html
        <label for="email">Email (nomprenom@domain.fr)</label>
        <input type="text" id="email" />
        ```
        Le format du champ email est donné directement dans le nom accessible.
    </Example>

    <Example comply>
        ```html
        <label for="date">Date de naissance</label>
        <input aria-describedby="aide-date erreur-date" type="text" id="date" />

        <p id="aide-date">Format : JJ/MM/AAAA</p>
        <p id="erreur-date">La date ne respecte pas le format. Ex. : 12/05/1985</p>
        ```
        Le format est donné par un passage de texte lié par la propriété `aria-describedby`
        et le message d’erreur fournit un exemple réel de saisie et également lié par la relation `aria-describedby`.
    </Example>
</details>

## Aide à la détection
<BookmarkletTags names={["11.1 Formulaires"]} />

- Avant d’activer le bookmarklet, remplir le formulaire avec des erreurs de saisie
(omettre le @ dans un champ email, écrire une date avec des lettres par ex.).
- Vérifier si des messages d’erreur mentionnent des formats non respectés.
- Pour les formats non respectés, vérifier la présence d’un format de saisie avant la soumission du formulaire,.
- Activer ensuite le bookmarklet, et pour tous les messages d’aides et les messages d’erreur,
vérifier qu’ils sont correctement reliés au champ, en constatant la présence d’un texte après « Description ».

## Cas particuliers

Le test 11.10.1 et le test 11.10.2 seront considérés comme non applicables lorsque le formulaire comporte
un seul [champ de formulaire](https://accessibilite.numerique.gouv.fr/methode/glossaire/#champ-de-saisie-de-formulaire)
ou qu’il indique les champs optionnels de manière :

*   Visible
*   Dans la balise `<label>` ou dans la [légende](https://accessibilite.numerique.gouv.fr/methode/glossaire/#legende)
associée au champ.

Dans le cas où l’ensemble des champs d’un formulaire sont obligatoires, les tests 11.10.1 et 11.10.2 restent applicables.

## Notes techniques

Dans un long formulaire dont la majorité des champs sont obligatoires, on pourrait constater que ce sont
les quelques champs restés facultatifs qui sont explicitement signalés comme tels. Dans ce cas, il faudrait
s’assurer que :
*   Un message précise visuellement en haut de formulaire que “tous les champs sont obligatoires sauf ceux indiqués
comme étant facultatifs”
*   Une mention “facultatif” est présente visuellement dans le libellé des champs facultatifs ou dans la
légende d’un groupe de champs facultatifs
*   Un attribut `required` ou `aria-required="true"` reste associé à chaque champ qui n’est pas concerné
par ce caractère facultatif.
